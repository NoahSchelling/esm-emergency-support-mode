## 2. 深刻度：高

### CS-01 コミットメッセージ、作成者とコミッター、ブランチ名、タグのメッセージを検査しない

**内容**：プッシュの検査（`--push`、`--range`）は `git log --format='commit %H'` で差分だけを読み、コミットのハッシュしか出力していない。そのため次のものは一度も検査されない。どれも公開リポジトリでは誰でも読める。

- コミットメッセージ（本文と末尾の行を含む）
- 作成者とコミッターの名前とメールアドレス（`git config user.email` に個人のアドレスを入れたまま作業すると、すべてのコミットに入る）
- ブランチ名（pre-push には送り先の参照名が渡るが、使っていない）
- 注釈付きタグのメッセージとタガーの情報

ステージの検査（pre-commit）は、仕組みとしてコミットメッセージを見られない（pre-commit の時点ではまだ書かれていない）。

**再現の手順**：

1. `echo ok > t1.txt && git add t1.txt && git commit -m "add file, key $KEY"` → 通した。`git push origin HEAD` → 通した。CI も通した。
2. `git commit -m "by $WORD <$MAIL>"` → コミット・プッシュ・CI すべて通した。
3. `GIT_AUTHOR_NAME="$WORD" GIT_AUTHOR_EMAIL="$MAIL" GIT_COMMITTER_EMAIL="$MAIL" git commit -m normal` → すべて通した。
4. `git checkout -b "feature/$WORD"` でブランチを作り、普通のコミットをしてプッシュする → すべて通した。
5. `git tag -a lab-tag -m "release by $WORD $MAIL"` のあと `git push origin lab-tag` → 通した。

**深刻度：高**。秘密情報と個人情報が漏れる経路のうち、いちばんうっかり起きやすい（設定の残ったメールアドレス、メッセージへのエラー出力の貼り付け、名前の入ったブランチ名）。手元のフックと CI の両方をすり抜ける。いったん公開されると、履歴を書き換えないと消せない。

なお、今の履歴の作成者とコミッターのメールアドレスは、すべて GitHub の noreply アドレスか、Claude の共同作成者のアドレスだった（ドメインだけを数えて確かめた）。今のところ漏れはない。

**修正案**：

- `--push` と `--range` で、各コミットの `%an %ae %cn %ce` とメッセージ（`%B`）も `check_text` にかける。`git log --format` の出力の先頭に、差分の行と混ざらない目印を付ける（たとえば行の先頭に、差分の行では出ない文字を付ける）。
- 作成者とコミッターのメールアドレスは、許可するドメイン（noreply と、共同作成者の行に使うドメイン）以外を止める。
- コミットメッセージの検査には Git の `commit-msg` フックを足す（手元で、プッシュより前に止められる）。
- pre-push で、送り先の参照名（`remote_ref`）とタグのメッセージ（`git cat-file -p` で読める）も検査する。

### CS-02 Git がバイナリとみなしたファイルは中身を検査しない

**内容**：検査は `git diff` の出力のうち、`+` で始まる行だけを見ている。Git がバイナリと判断したファイルは「Binary files ... differ」の 1 行になり、中身は 1 行も検査されない。バイナリ扱いになるのは次のとき。

- ファイルの先頭の部分に NUL のバイトがある。**UTF-16 のテキストもこれに当たる**。Windows の PowerShell 5 で `>` を使って出力を保存すると、UTF-16 のファイルになる。
- `.gitattributes` に `-diff` や `binary` を書いたファイル。**この指定はリポジトリに入るので、CI でも同じようにすり抜ける**。サブディレクトリに置いた `.gitattributes` でも効く。
- 圧縮ファイル、画像、PDF、Office の文書。画像の Exif には撮影した位置が入りうる。Office の文書には、作成者の名前（多くは本名）が入る。

**再現の手順**（どれも `git add` のあと `scripts/check-secrets.sh --staged` で確かめた）：

1. `printf '%s\n' "key=$KEY" "mail=$MAIL" | iconv -f UTF-8 -t UTF-16LE > t/a.txt` → 通した。差分は「Binary files /dev/null and b/t/a.txt differ」の 1 行だけだった。
2. `{ printf '\0\n'; printf '%s\n' "key=$KEY"; } > t/a.txt` → 通した。
3. `printf '%s\n' "key=$KEY" > t/a.txt; printf 't/a.txt -diff\n' > .gitattributes` として、2 つともステージする → 通した。
4. 3 と同じことを、`t/.gitattributes` に `* binary` と書いて行う → 通した。
5. キーを書いたファイルを gzip で圧縮してステージする → 通した。

**深刻度：高**。3 は 1 行で検査を無効にでき、CI でも同じように通る。1 は、うっかりでも起きる（Windows で作った設定やログの保存）。

**修正案**：

- 差分を取るときに `--text`（`-a`）を付け、属性に関係なくテキストとして扱う。あわせて `--no-textconv` を付け、手元の変換の設定に左右されないようにする。
- UTF-16 は、BOM か NUL の並び方で見分け、UTF-8 に変換してから検査する。
- `.gitattributes` に `-diff`、`binary`、`diff=`、`filter=` を足す変更は止めるか、少なくとも警告する。
- バイナリのファイルは「中身を検査していない」と警告に出す。拡張子の許可リスト（画像など）にないものは止める。画像はメタデータを消してから入れることを約束にする（`exiftool -all=` など）。

### CS-03 種類の変更（シンボリックリンクから通常のファイル）を検査から外している

**内容**：差分の対象を `--diff-filter=ACMR` で絞っている。ここに T（種類の変更）が入っていないため、シンボリックリンクを通常のファイルに置き換えたとき、そのファイルの中身を見ない。逆向き（通常のファイルからシンボリックリンク）も同じ。

**再現の手順**：

1. `ln -s README.md link.txt && git add link.txt && git commit -m link` → 通した（リンク先のパスは検査された）。
2. `rm link.txt && printf '%s\n' "key=$KEY" > link.txt && git add link.txt` → `git diff --cached --name-status` には「T link.txt」と出る。`scripts/check-secrets.sh --staged` の結果は「ファイル=0 追加行=0」で、通した。
3. コミット、プッシュ、CI のすべてで通した。

**深刻度：高**。2 回のコミットでできて、3 つの守りのすべてをすり抜ける。わざとでなくても、リンクを実体のファイルに置き換える整理は普通に行う。

**修正案**：`--diff-filter` に T を足す（`ACMRT`）。いっそ、`--diff-filter=d`（削除だけを除く）のように、除くほうを書く形にする。そうすれば、Git に新しい種類が増えても漏れない。

### CS-04 ステージと「フックを外したコミット」を 1 回のコマンドで行うと、二重の守りを両方すり抜ける

**内容**：Claude Code のフックは、コマンドを実行する**前**にステージ済みの変更を検査する。CLAUDE.md にあるとおり、同じコマンドの中でステージした分は、Git の pre-commit フックが拾う前提になっている。ところが、同じコマンドの中で Git のフックも外すと、どちらの守りも働かない。外し方は 2 つ確かめた。

- `git -c core.hooksPath=/dev/null commit`（そのコマンドだけフックの場所を変える）
- `git commit --no-verify`

CLAUDE.md は `--no-verify` を禁止しているが、仕組みで止めてはいない。プッシュも同じで、`git -c core.hooksPath=/dev/null push` は pre-push を外す。

**再現の手順**（Claude Code のフックが受け取るのと同じ形の JSON を `scripts/claude-hook-bash.sh` に渡し、そのあと同じコマンドを実行した）：

| コマンドの形（キーを書いたファイルは、ステージ前） | Claude Code のフック | 実行の結果 |
| --- | --- | --- |
| `git add k.txt && git commit -m x` | 通した（終了コード 0） | Git のフックが止めた |
| `git add k.txt && git -c core.hooksPath=/dev/null commit -m x` | 通した | コミットされた |
| `git add k.txt && git commit --no-verify -m x` | 通した | コミットされた |

プッシュの検査も、`git -c core.hooksPath=/dev/null push` で外せることを確かめた（このケースでは CI だけが止めた）。

**深刻度：高**。守りを止める操作が、一般的な Git の機能でできる。Claude が「誤検出だから」と判断してこの形を選ぶ恐れもある（プロンプトインジェクションでも起こりうる）。

**修正案**：

- `scripts/claude-hook-bash.sh` で、コマンドに `--no-verify`、`-n` を含む `git commit`、`core.hooksPath`、`git push` の `--no-verify` が入っていたら止める。
- Claude Code のフックの検査を「実行前のステージ済みの変更」ではなく「実行前のステージ済みの変更と、作業ツリーの未ステージの変更の両方」にする（`git diff HEAD` 相当。ステージしそうなものを先に見る）。
- `.claude/settings.json` の `permissions.deny` に、フックを外すコマンドの形を入れる（仕組みで止める層をもう 1 つ増やす）。
- 最後の守りは CI になるので、CS-11 の「必須の検査」を設定する。

### CS-05 検査を止める変更を、その変更自体と一緒に通せる

**内容**：検査の仕組み自体を壊す変更を、検査が拾わない。

- `.githooks/pre-commit` の実行権限を外すコミット（ファイルのモードを 100755 から 100644 にする）。チェックアウトした人の環境では、Git がフックを無視する。そのとき出るのは hint の 1 行だけで、コミットは成功する。
- 作業ツリーの `scripts/check-secrets.sh` を、何もせずに 0 で終わる中身に書き換える。Git のフックは作業ツリーのスクリプトを実行するので、以後の検査はすべて通る。
- **CI は、PR の側のワークフローとスクリプトで動く**。PR の中で `scripts/check-secrets.sh` やワークフローを書き換えると、その PR の CI は書き換えた版で動く。

**再現の手順**：

1. `chmod -x .githooks/pre-commit && git add .githooks/pre-commit && git commit -m chmod` → 通した。`git ls-files -s` でモードが 100644 になったことを確かめた。続けてキーを書いたファイルをコミットすると、hint が出たうえで、コミットは成功した（プッシュは pre-push が止めた。pre-push の実行権限も同じように外せる）。
2. `printf '#!/usr/bin/env bash\nexit 0\n' > scripts/check-secrets.sh` としたあと、キーを書いたファイルのコミットとプッシュ → どちらも通した。
3. 2 の書き換えとキーを同じコミットに入れ、そのコミットにあるスクリプトで `--range` を走らせる（PR の CI と同じ条件） → 通した。

**深刻度：高**。1 回の変更で、手元の守りと CI の守りを止められる。1 は、Windows など実行権限を保てない環境から編集しただけでも起きうる。

**修正案**：

- 検査の中で、`.githooks/`、`scripts/check-secrets.sh`、`scripts/claude-hook-bash.sh`、`.claude/settings.json`、`.github/workflows/` への変更を検知し、警告を出す。モードの変更は止める。
- CI では、検査のスクリプトを PR の版ではなく、ベースのブランチ（main）の版から取り出して実行する（`git show "$PR_BASE:scripts/check-secrets.sh"`）。
- GitHub に `CODEOWNERS` を置き、上のファイルへの変更には持ち主のレビューを必須にする（ブランチ保護と組み合わせる）。
- pre-commit と pre-push の中で、自分（フックのファイル）とスクリプトの実行権限と内容のハッシュを確かめる案もある。ただし、作業ツリーの改ざんには、根本的には効かない。

## 3. 深刻度：中

### CS-06 日本語の個人語の表記のゆれと文字コードの違いを拾えない

**内容**：禁止語の検査は「小文字にした行に、禁止語がそのまま含まれるか」だけを見ている。小文字にするのは ASCII だけで（`LC_ALL=C`）、Unicode の正規化はしない。そのため次の書き方は、どれも通る。日本語の文書では、姓と名の間に空白を入れる書き方がごく普通にある。

**再現の手順**（`$WORD` と `$WORD_JA` を禁止語リストに入れて、`--staged` で確かめた）：

| 書き方 | 結果 |
| --- | --- |
| そのまま（英字、日本語とも） | 止めた |
| 英字の大文字と小文字を混ぜる | 止めた |
| 英字を全角にする | 通した |
| 途中にゼロ幅スペース（U+200B）を入れる（英字、日本語とも） | 通した |
| 途中にハイフンを入れる | 通した |
| 日本語の途中に空白を入れる（姓と名の間など） | 通した |
| 同じ読みをカタカナで書く | 通した |
| 英字の 1 文字を、形の似た別の文字（キリル文字、長い s）に置き換える | 通した |
| 日本語の語を Shift_JIS で保存した CSV | 通した |
| 日本語の語を EUC-JP で保存したテキスト | 通した |

Shift_JIS は、Excel で保存した CSV の既定の文字コードであり、うっかりでも起きやすい。

**深刻度：中**。うっかりの漏れ（空白入りの名前、Excel の CSV）が普通に起きる。ただし、禁止語リストが動いていないと、そもそも検査されない（CS-16）。

**修正案**：

- 行と禁止語の両方を、NFKC で正規化（全角を半角にする等）し、空白、ゼロ幅文字、ハイフン、中黒を除いてから比べる。bash だけでは難しいので、`python3 -I` が使える環境では Python で比べる（使えないときは今の比べ方に戻し、そのことを表示する）。
- 文字コードを判定し（UTF-8 として正しくない行がある、など）、Shift_JIS と EUC-JP は `iconv` で UTF-8 にしてから検査する。判定できないときは警告する。
- 禁止語リストの書き方の説明に「漢字・かな・カナ・ローマ字の表記を全部書く」ことを足す。

### CS-07 分けて書いたキーや、符号化したキー・メールアドレスを拾えない

**内容**：検査は 1 行ずつ、決まった形の文字列だけを探している。そのため次の書き方は通る。わざとでないと起きにくいものが多い。ただし、パーセント符号化と JSON の `@` は、URL や JSON を出力した道具の結果として、うっかりでも起きる。

**再現の手順**（`--staged`）：

- キーを 2 行に分ける → 通した
- Python で `'前半' + '後半'` のように文字列をつなぐ → 通した
- キーを base64、16 進、逆順にする → 通した
- メールアドレスの `@` を、`%40`、`&#64;`、` [at] `、全角の `＠`、JSON の `@` にする → どれも通した

**深刻度：中**。キーそのものの漏れは、わざとでないと起きにくい。メールアドレスは、うっかりでも起きる形がある。

**修正案**：

- メールアドレスの規則に、`%40`、`&#64;`、`@`、全角の `＠` も入れる。
- 長い base64 や 16 進の文字列を見つけたら、復号してから同じ規則にかける（深追いはしない。1 回だけ）。
- 分けて書いたキーは、仕組みで拾うのは難しい。GitHub の Secret scanning と push protection を有効にして、別の層にする（公開リポジトリでは無料で使える）。

### CS-08 規則のない形の秘密情報

**内容**：規則は 6 種類（Anthropic、AWS のアクセスキー ID、AWS の秘密キー、GitHub の 2 種類のトークン、秘密鍵の開始行）だけ。CLAUDE.md が禁止している「パスワード」には規則がない。AWS の秘密キーの規則は、近くに「aws」と「secret」がアンダースコアでつながって書かれているときだけ当たる。

**再現の手順**（`--staged`。どれも通した）：

- `aws sts` が出す JSON の形（キーの名前が SecretAccessKey）に 40 文字の値を入れる
- `aws-secret-access-key = ...`（ハイフンでつなぐ書き方）
- Terraform の `secret_key = "..."`
- `password = "..."`
- パスワード入りの接続文字列で、ホストが IP アドレスのもの（ホスト名がドメインなら、メールアドレスの規則に偶然当たって止まる）
- `Authorization: Bearer` に続く長い値
- Slack や Google の API キーと同じ形の値、JWT と同じ形の値
- PuTTY の鍵ファイルの先頭行

**深刻度：中**。この試作で使うのは Anthropic と GitHub が中心だが、AWS の MCP や Google の各サービスが使える環境で作業している。パスワードの規則がないのは、CLAUDE.md の禁止事項との食い違いになる。

**修正案**：

- `password`、`passwd`、`secret`、`token`、`api_key` などの名前に、ある程度の長さの値を代入している行を止める（例の値やテスト用の値は、許可する書き方を決める）。
- URL の「ユーザー名:パスワード」の部分を止める（ホストの形は問わない）。
- AWS の秘密キーの規則の、名前の部分を広げる（区切りのハイフン、`SecretAccessKey`）。
- 主要なサービスのトークンの形を足す。網羅するのは無理なので、CS-07 と同じく GitHub の Secret scanning を併用する。

### CS-09 ファイル名の規則の抜け

**内容**：ファイル名の規則は `.env` の系統、`*.pem`、Claude Code の個人設定の 2 つだけ。`.gitignore` にはもっと多くの名前があるが、`git add -f` を使えば無視の設定を越えて入る。検査の側では見ていない。

**再現の手順**（`git add -f` のあと `--staged`）：

- `.ENV`（大文字） → 通した（`.env` の判定だけが大文字と小文字を区別している）
- `.envrc`、`id_rsa`（中身に開始行がない場合）、`cert.p12`、`server.key`、パスワード入りの `.netrc` → どれも通した
- 逆に `.env.sample` は止めた（`.env.example` だけが許されている）。これは誤検出になりうる。

**深刻度：中**。

**修正案**：判定はすべて小文字にしてから行う。`.envrc`、`id_rsa*`、`id_ed25519*`、`id_ecdsa*`、`*.key`、`*.p12`、`*.pfx`、`*.ppk`、`*.keystore`、`.netrc`、`.npmrc`、`.pypirc`、`credentials*.json`、`.mcp.json`（トークンが入りやすい）を足す。`.env.sample` と `.env.template` は許す。`.gitignore` の「秘密情報」の節と、検査の規則を同じ一覧から作るようにすると、ずれない。

### CS-10 pre-push は、どれかのリモート追跡参照にあるコミットを「検査済み」とみなす

**内容**：`--push` は `--not --remotes` で、手元の**すべての**リモート追跡参照（`refs/remotes/*`）から辿れるコミットを除く。この参照は手元で自由に作れる。また、送り先とは別のリモート（フォークなど）から取り込んだコミットも除かれる。

**再現の手順**：

1. キーを入れたコミットを作り、`git update-ref refs/remotes/somefork/x <そのコミット>` としてからプッシュする → pre-push は通した（CI は止めた）。
2. 別のリモート `fork` を足し、キーを入れたコミットを相手の側にだけ置く（相手が自分でプッシュした状態の再現）。`git fetch fork` のあと、そのコミットを `origin` にプッシュする → pre-push は通した（CI は止めた）。

**深刻度：中**。2 は、他人の PR を手元で取り込んで公開のリポジトリへ送るときに、うっかり起きる。CI が PR と main で拾うが、main 以外のブランチへの直接のプッシュは CI が見ない（CS-11）。

**修正案**：pre-push では、渡された `remote_sha` を使う。送り先の参照の今の値（`<remote_sha>`）と、プッシュ先のリモートの追跡参照（`refs/remotes/<remote名>/*`）だけを除外の基点にする。新しい参照のときは、送り先のリモートの追跡参照だけを使う。

### CS-11 CI が見ない経路がある。main への push の検査は事後になる

**内容**：ワークフローは `pull_request` と、`main` への `push` でしか動かない。次の経路は CI が見ない。

- main 以外のブランチへの直接のプッシュ（PR を作らない場合）。公開リポジトリでは、ブランチも公開される。
- タグのプッシュ。
- GitHub の画面での、main 以外のブランチの編集（PR がない場合）。
- GitHub の MCP の `push_files`、`create_or_update_file` などで直接コミットを作る経路。手元の Git のフックも、Claude Code のフック（Bash ツールだけが対象）も通らない。この環境では、これらの道具が使える状態になっている。

また、`main` への push の CI は、**公開されたあと**に走る。止める働きはない。PR の CI が、マージに必須の検査になっているかどうかは確かめていない（このセッションでは GitHub の MCP に接続できなかった。要確認）。

**再現の手順**：`.github/workflows/check-secrets.yml` の `on:` を読んで確かめた。実際の GitHub への送信はしていない。

**深刻度：中**。

**修正案**：

- `push` の対象を全ブランチとタグにする（`branches: ['**']`、`tags: ['**']`）。
- ブランチ保護（ルールセット）で、この検査をマージの必須条件にする。main への直接のプッシュを禁止する。
- GitHub の Secret scanning の push protection を有効にする（GitHub の側で、プッシュそのものを止められる。ただし、個人語は対象外）。
- `.claude/settings.json` の PreToolUse の対象に、GitHub の MCP の書き込み系の道具を足す。足せない間は、`permissions.deny` で使えなくしておく。

### CS-12 人間の手元では、Git のフックが既定で動かない

**内容**：`core.hooksPath` を設定するのは、Claude Code の SessionStart フックだけ。人がクローンして作業すると、Git のフックは一切動かない。README には、設定の手順が書かれていない（CLAUDE.md の表にはあるが、手順として目立たない）。

**再現の手順**：新しくクローンした直後に `git config --get core.hooksPath` が空であることと、README に設定の記述がないことを確かめた。

**深刻度：中**。CI が PR と main で拾うが、CS-11 の経路では拾わない。

**修正案**：README に「クローンしたら最初に実行する」として `git config core.hooksPath .githooks` を書く。スクリプトの側でも、`--range` 以外のモードで `core.hooksPath` が設定されていなければ注意を出す（手動で走らせたときに気づける）。

### CS-13 検査の出力が、ファイル名を伏せずに出す

**内容**：見つけた値は、先頭 2 文字と長さだけに伏せている（`mask`）。ところが、場所を示す「パス」は伏せていない。ファイル名に禁止語やメールアドレスが入っていると、出力にそのまま出る。

- 手元：Claude Code のフックが止めたときの出力は、Claude にそのまま渡る。Claude がその出力を開発ログに引き写すと、禁止語が文書に入る（禁止語の検査が動いていない環境では、それも止まらない）。
- CI：公開リポジトリの Actions のログは、誰でも読める。ブランチを消して漏れを片付けても、ログは保存期間のあいだ残る。GitHub は Secrets の値を伏せるが、ファイル名に含まれる語は Secrets の値（複数行の全体）と一致しないので、伏せられないと考えられる（GitHub が複数行の Secrets を行ごとに伏せるかどうかは、確かめていない。要確認）。

**再現の手順**：

1. `t/<禁止語>.md` という名前のファイルをステージして `--staged` を走らせる → 「停止: t/（禁止語そのもの）.md(ファイル名): 個人語に一致（禁止語リストの 2 行目）」と出た。
2. メールアドレスを名前に含むファイルでは、値は伏せられたが、同じ行の「場所」の部分にアドレスがそのまま出た。
3. `.env` の判定の行も、パスを 2 回出す。

**深刻度：中**。

**修正案**：ファイル名で当たったときは、パスを伏せて出す（何番目のファイルか、ディレクトリだけ、ハッシュの先頭など）。本文で当たったときも、パスに当たりがあれば伏せる。伏せた値は、先頭 2 文字も出さず、長さと規則の名前だけにする案もある（先頭 2 文字は、メールアドレスでは本名の頭文字になりうる）。

### CS-14 禁止語リスト（Secrets）は、同じリポジトリのブランチからの PR で取り出せる

**内容**：`pull_request` のイベントは、同じリポジトリのブランチからの PR なら、リポジトリの Secrets を読める。ワークフローは PR の側の版で動く（CS-05）。そのため、書き込みの権限を持つ人（またはその権限で動く Claude のセッション）は、PR の中でワークフローを書き換え、`ESM_DENYLIST` を変換して（たとえば base64 にして）ログに出せる。変換すると、GitHub の伏せる仕組みにかからない。禁止語リストは個人情報そのもの（本名、住所の一部など）なので、漏れると、守りたいものがまとめて漏れる。

**再現の手順**：ワークフローの設定を読んで確かめた。実際の Secrets を使った試しはしていない（試すこと自体が漏洩になる）。

**深刻度：中**。今は書き込みできる人が限られている。だが、Claude のセッションがプロンプトインジェクションを受けた場合にも起こりうる。

**修正案**：

- 禁止語そのものではなく、正規化した語のハッシュ（ソルト付き）を Secrets に置き、行の側の部分文字列をハッシュして比べる。CI のログや、ワークフローの改ざんで漏れても、語は直接は読めない（長さごとに部分文字列をハッシュするので、計算量は増える）。
- または、禁止語の検査を `pull_request` では行わず、Environments の承認付きのジョブ（main のワークフローの版）だけで行う。
- `.github/workflows/` の変更に、持ち主のレビューを必須にする（CS-05）。

### CS-15 長い行で処理時間が長さの 2 乗に比例して増える

**内容**：メールアドレスの規則は、アドレスの前の部分（英数字と `. _ % + -`）が長く続くと、bash の正規表現の照合が、行の長さの 2 乗に比例して遅くなる。ほかの 7 つの規則は、同じ行でもすぐに終わった。

**再現の手順**（`--staged`、作業用の環境で計測）：

| 入力 | 時間 |
| --- | --- |
| 同じ英字 3 万文字の 1 行に、メールアドレスの規則だけをかける | 約 2 秒 |
| 同じ英字 30 万文字（300KB）の 1 行のファイル | 約 220 秒 |
| 同じ英字 100 万文字（1MB）の 1 行のファイル | 300 秒で打ち切り |
| 10 万行の CSV（行は短い） | 約 12 秒 |
| 許可されたドメインのアドレス 8000 件を並べた 1 行 | 約 6 秒 |
| 参考：今の全履歴（160 ファイル、約 2.7 万行） | 約 3.7 秒 |

**深刻度：中**。区切りのない長い文字列（圧縮した JavaScript の一部、SVG のパスのデータ、区切りのない 16 進の並びなど）は、データを扱うこの試作でありうる。

- Git のフックには時間の上限がない。数分止まると、`Ctrl-C` のあとで `--no-verify` を使いたくなる（CS-04）。
- Claude Code のフックには時間の上限がある。上限を超えたときにコマンドが止まるのか、そのまま実行されるのかは、公式の説明で確かめていない（要確認）。そのまま実行されるなら、守りが外れる。
- CI は `timeout-minutes: 10` で打ち切られて失敗する（止まる側なので安全だが、原因が分かりにくい）。

**修正案**：

- メールアドレスの規則にかける前に、`@` を含まない行は飛ばす（ほとんどの長い行がここで終わる）。`@` の前後の、決まった長さ（たとえば前に 64 文字、後ろに 255 文字）だけを切り出して照合する。
- 1 行が決まった長さ（たとえば 10KB）を超えたら、長い行として警告し、切り出した部分だけを検査する。
- 全体の行数が多いときは、`grep -E` でまとめて当たりを探し、当たった行だけを bash で詳しく見る（`grep` は 1 回の起動で済む）。

### CS-16 個人語の検査が、実際にはほとんど動いていない

**内容**：

- クラウドの Claude Code のセッションでは、`ESM_DENYLIST_FILE` が設定されていない。開発ログ（s04 など）にも「未実施」と書かれている。この回も未実施だった。
- 「未実施」の注意は毎回出るので、見慣れて読まれなくなる。
- CI の禁止語の検査は、Secrets に `ESM_DENYLIST` が登録されているときだけ動く。登録されているかどうかは確かめていない（要確認）。

その結果、日本語の本名や地名の漏れを止める仕組みは、人の目だけになっている。

**深刻度：中**。CS-06 と重なると、表記を少し変えただけでも、機械では拾えない。

**修正案**：

- CI の Secrets への登録を確かめる。登録したら、CI の出力で「個人語の検査を実施（禁止語 N 件）」となることを、開発ログで毎回確かめる。
- 公開の 11/8 までは、`main` への push で個人語の検査が「未実施」なら、CI を失敗にする（警告ではなく停止）。
- クラウドのセッションには、環境変数ではなく、環境のシークレットの機能で禁止語リストを渡す方法を検討する（リポジトリの外に置く条件は保つ）。

### CS-17 誤検出

**内容と再現の手順**（`--staged`）：

- README などに書く SSH 形式のクローン URL（ユーザー名 git と github.com を `@` でつないだ形） → 止めた
- 共同作成者の行（`Co-Authored-By:` に Claude の noreply のアドレス）を、文書の中で例として書く → 止めた
- `ssh` の「ユーザー名と host.local を `@` でつないだ形」 → 止めた
- `.env.sample`、`.env.template` → 止めた
- 短い禁止語の部分一致：試しに英字 3 文字の語（ある人名の短縮形にありうるもの）を禁止語リストに入れて全履歴を検査すると、14 か所で止まった（英単語の一部に含まれるため）。日本語の 1〜2 文字の姓でも、同じことが起きる。

今の全履歴では、停止も警告も 0 件だった。誤検出は、今はまだ少ない。

**深刻度：低**。ただし、誤検出が続くと、`--no-verify`（CS-04）や、禁止語リストから語を消す方向に流れやすい。

**修正案**：

- メールアドレスの許可リストに、SSH の git ユーザーの形（`git` と `github.com`）と、共同作成者の行の noreply のアドレスを足す。または、許可するアドレスの一覧を、リポジトリの中の 1 つのファイルにまとめる（アドレスそのものではなく、ドメインと用途を書く）。
- 禁止語には「単語の境界で比べる」印を付けられるようにする（英字の語だけ。日本語は境界がないので、短い語は登録しないよう説明する）。
- 誤検出を許すための注記（行の末尾に特定のコメントを書くと、その行を飛ばす）は入れないほうがよい。すり抜けの手段になるため。

### CS-18 Claude Code のフックの判定をすり抜けるコマンドの書き方がある

**内容**：`claude-hook-bash.sh` は、コマンドの文字列から「git、オプション、サブコマンド」の並びを正規表現で探す。次の書き方は、検査そのものが行われなかった（Git のフックは別に動くので、CS-04 と組み合わさないかぎり、二重の守りの片方が抜けるだけ）。

**再現の手順**（ステージ済みのキーがある状態で、フックに JSON を渡した）：

| 書き方 | 結果 |
| --- | --- |
| `git commit`（対照） | 止めた |
| `sh -c 'git commit ...'`、`git --git-dir=.git ... commit`、`GIT_DIR=.git git commit` | 止めた |
| `/usr/bin/git commit`（絶対パス） | 検査しなかった |
| `"git" commit`、`'git' commit`（引用符付き） | 検査しなかった |
| `g=git; $g commit`（変数） | 検査しなかった |
| `git ci`（エイリアス） | 検査しなかった |
| `git {commit,}`（中かっこの展開） | 検査しなかった |
| `git` と `commit` の間に、改行の継続やタブ | 検査しなかった |
| `bash ./do-it.sh`、`make release`、Python からの呼び出し | 検査しなかった |
| `git commit-tree`（下位のコマンド） | 検査しなかった |

ほかに分かったこと：

- `git -C <別の場所> commit` でも、検査するのは `CLAUDE_PROJECT_DIR` のリポジトリだけ（このリポジトリの外で作業するときは、関係ない検査が走る）。
- `echo 'git commit ...'` のように、文中に出てくるだけでも検査が走る（このセッションでも、作業用の場所でのコマンドのヒアドキュメントに反応した）。ステージに問題が残っていると、関係ないコマンドまで止まる。
- `git commit-tree` と `git cherry-pick` で作ったコミットは pre-commit を通らないが、pre-push が止めた（守りとして働いている）。

**深刻度：低**。

**修正案**：文字列の照合で網羅するのは無理なので、Claude Code のフックは「補助」と位置づける。そのうえで、Bash のコマンドに `commit`、`push`、`hooksPath`、`--no-verify` のどれかの語が入っていれば、場所を問わず検査する（誤って広く当たってもよい）。確実に止める役目は、Git のフックと CI（必須の検査）に任せる。

### CS-19 手元の Git の設定で検査が弱まる

**内容**：スクリプトは Git の設定を固定していない。手元の設定や環境変数で、次のように検査が弱まる。わざとでないと起きにくい。

**再現の手順**：

- `log.showRoot=false` を設定すると、最初のコミット（親のないコミット）の差分が出なくなり、キーを入れた最初のコミットの `--range` が通った（既定の設定では止めた）。
- `core.attributesFile` に `* -diff` と書いたファイルを指すと、すべてのファイルがバイナリ扱いになり、`--staged` が通った（CS-02 の手元版）。
- `git replace` で、キーを入れたコミットを、きれいな中身のコミットに見せかけると、pre-push は通した。実際にリモートへ送られたのは、キーを入れた元のコミットだった（CI には replace の参照が渡らないので、実際の CI は止めるはず）。

**深刻度：低**。

**修正案**：Git の呼び出しに、`-c log.showRoot=true -c core.attributesFile=/dev/null --no-replace-objects` を付ける（CS-02 の `--text --no-textconv` とあわせる）。`GIT_CONFIG_*` などの環境変数で設定を足されている場合は、警告を出す。

### CS-20 禁止語ファイルの「リポジトリ内なら止める」判定は、シンボリックリンクで回避できる

**内容**：判定では、ディレクトリのシンボリックリンクは解決するが、ファイルそのもののシンボリックリンクは解決しない。リポジトリの外に、リポジトリの中のファイルを指すリンクを置き、それを `ESM_DENYLIST_FILE` に指定すると、判定を通る。

**再現の手順**：リポジトリの中に禁止語ファイルを置き、直接指定すると止まった。リポジトリの外のリンクを経由すると「個人語の検査を実施」となった。ただし、そのファイル自体をステージすると、中の語が自分自身に一致して止まった（コミットはされない）。

**深刻度：低**。

**修正案**：`readlink -f`（または `realpath`）でファイルまで解決してから比べる。macOS の大文字と小文字を区別しないファイルシステムを考え、比べるときは両方を小文字にする。

### CS-21 コミットの日時のタイムゾーンから、住んでいる地域の手がかりが出る

**内容**：今の履歴では、人が作ったコミットの日時が +0900 になっている（Claude のセッションのコミットは +0000）。日本に住んでいることは README などからも分かるので、今は問題にならない。ただ、時刻の並びから生活の時間帯も読み取れる。

**深刻度：低**。

**修正案**：気になるなら、コミットのときに `TZ=UTC` を使う。CLAUDE.md の「個人情報」の範囲に、タイムゾーンを入れるかどうかを決める。

### CS-22 macOS 標準の古い bash では動かない書き方を使っている（未検証）

**内容**：スクリプトは `${変数,,}`（小文字への変換）など、bash 4 以降の書き方を使っている。macOS が最初から持っている bash は 3.2 なので、`#!/usr/bin/env bash` でこれが選ばれると、エラーになる。止まる側に倒れるのか、検査を飛ばして 0 で終わるのかは、確かめていない（この環境に bash 3.2 がない）。止まる側なら、毎回コミットが止まるので、フックを外す方向に流れる。

**深刻度：低**（参加者が macOS を使うなら上がる）。

**修正案**：スクリプトの冒頭で `BASH_VERSINFO` を確かめ、4 未満なら、理由を出して終了コード 2 で止める（止まる側に倒すことを明示する）。README に「bash 4 以上が必要（macOS は Homebrew などで入れる）」と書く。

## 5. 確かめた範囲で、守りとして働いていたもの

- 差分の読み取りは堅かった。内容の行は必ず 1 文字の印で始まるため、ファイルの中身で `commit`、`diff --git`、`+++` の行を偽装して、場所の追跡を狂わせることはできなかった。
- `git commit -a` と `git commit <パス>`（一時的なインデックスを使う形）でも、pre-commit は正しくキーを止めた。
- `git commit-tree` と `git cherry-pick` で作ったコミットは pre-commit を通らないが、pre-push が止めた。
- `git notes` に書いたキーは、ノートの参照をプッシュするときに止めた。
- シンボリックリンクのリンク先のパスも、テキストとして検査された（禁止語を含むリンク先を止めた）。
- Claude Code のフックは、検査が 0 以外で終わったら必ず止める（止まる側に倒れる）作りになっていた。
- CI は、チェックアウトのアクションをコミットのハッシュで固定し、認証情報を残さず、イベントの値を環境変数で渡している（スクリプトに値を埋め込まないので、注入されない）。
- 見つけた値の本文は、先頭 2 文字と長さだけに伏せて出していた。
- 今の全履歴（160 ファイル、約 2.7 万行）は、停止 0、警告 0。約 3.7 秒で終わった。

## 6. 確かめていないこと（要確認）

- Claude Code のフックが時間の上限を超えたとき、コマンドが止まるのか、そのまま実行されるのか（CS-15）。
- PR の CI が、マージの必須条件になっているか。main への直接のプッシュが禁止されているか（CS-11）。このセッションでは GitHub の MCP に接続できなかった。
- リポジトリの Secrets に `ESM_DENYLIST` が登録されているか（CS-16）。
- GitHub が、複数行の Secrets をログの中で行ごとに伏せるか（CS-13）。
- macOS の bash 3.2 での動き（CS-22）。
- Windows（Git for Windows）で、フックの実行権限がどう扱われるか（CS-05）。
- Git LFS を使った場合。LFS のファイルの中身は Git の差分に出ないので、検査されないと考えられる（今は LFS を使っていない）。

## 付録 A：偽の値の作り方（言葉で）

- どの値も、作業用の場所に置いたシェルのスクリプトの中で、実行のたびに断片をつないで作った。スクリプトのファイル自体には、規則に当たる形の文字列がない。
- Anthropic の形のキー：キーの接頭辞を 3〜4 個の断片に分けて書き、実行時につなぐ。後ろに、同じ英大文字を 40 個つなぐ。
- GitHub の形のトークン：接頭辞の 2 文字と、続きの文字を分けて書き、同じ英大文字を 36 個つなぐ。
- AWS のアクセスキー ID：接頭辞の 4 文字を 2 つに分けて書き、同じ英大文字を 16 個つなぐ。
- 秘密鍵の開始行：行を 4 つの断片に分けて書いてつなぐ。
- メールアドレス：アドレスの前の部分と、使われない予約ドメイン（`.invalid` で終わる名前）を、`@` を別の変数に入れてつなぐ。
- 禁止語：意味のない架空の英字の語と、架空の日本語の語（漢字 4 文字）を、作業用の場所の禁止語ファイルにだけ書いた。

実験が終わったあと、偽の値を含む複製とベアリポジトリは消した。
