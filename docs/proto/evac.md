# 試作：避難場所への直線の方向（modules/evac/ と app/ の避難者の表示）

- 作成日：2026-11-07（日本時間）
- 置き場所：`modules/evac/`（計算）、`app/evac/`（避難者の表示）。使い方は [modules/evac/README.md](../../modules/evac/README.md) と [app/README.md](../../app/README.md)。
- 状態：**試作**。実機ではまだ確かめていません。パソコンの Chrome（Playwright）と Node.js でだけ確かめました。向きのイベントは、すべてスクリプトで作った偽物です。

このページの一番大事な方針：**誤った向きの矢印を出さないことを、正しい矢印を出すことより優先する。** 実機で少しでも疑わしい結果が出たら、矢印を出す条件を厳しくする（または矢印をやめて文と北を上にした図だけにする）。

## 2. 実機で確かめるべき点

### 2.1 コンパスのずれ（金属や車の近く）

- 鉄骨の建物の中、車の中・車のそば、ガードレール・鉄の柵・自動販売機のそば、電車の中で、方位がどれだけずれるか。
- 確かめ方：見通しのよい場所で、方向が分かっている目標（地図で方位を測った建物など）に端末の上を向け、画面の「北から○度」と比べる。同じ場所で、金属に近づけたときの変化を見る。
- iPhone：`webkitCompassAccuracy` がずれに応じて大きくなるか（ずれているのに精度が「よい」と出ることがないか）。
- Android：精度の値がないので、ずれていても「安定している」と見える。そのため、GPS の進行方向と一致してから 20 秒（！！仮の値！！）のあいだだけ矢印を出すことにした（止まったままでは出ない。歩いているあいだは一致し続けることを求める）。実機で、歩き始めてから矢印が出るまでの時間、曲がったあとに一致が崩れるまでの時間、止まってからの 20 秒のあいだに金属に近づいてずれた場合（この場合は検出できない）を確かめる。それでもずれが大きいなら、Android では矢印を出さず、文と図だけにすることを考える。
- 安定の検査（直近 1 秒の値のずれが 20 度以内）が、金属の近くで実際に働くか。働かないなら値を見直す。

### 2.2 校正の促し方

- iPhone：精度が負のとき、画面は「コンパスの校正が必要な場合があります」と出す。iPhone の校正の画面（8 の字に動かす）が自動で出るか、ブラウザからは出せないのかを確かめる。出ないなら、「端末を 8 の字を描くように動かす」の案内を足すか決める（文言は人が決める）。
- Android：校正の状態を知る方法がブラウザにない。Google マップなどの校正の案内を参考に、文言を足すか決める。
- 校正の案内で、利用者が立ち止まって時間を使うことの是非（発災直後の避難を遅らせないか）。

### 2.3 画面の回転

- 縦向き・横向き（左に倒す・右に倒す）・上下逆で、矢印が同じ方向（目標の方向）を指し続けるか。**符号（足すか引くか）は実機でしか確かめられない。** 間違っていれば、横向きで 180 度違う向きを指す。
- iPhone の `webkitCompassHeading` が、画面の回転を自分で考慮した値かどうか（考慮済みなら、こちらで足すと二重になる）。
- 画面の回転を固定している端末（回転ロック）で、`screen.orientation.angle` が 0 のままになるか。
- 確かめ終わるまでは、横向き・上下逆のときに矢印を出さない（`allowLandscape: false`、！！仮の値！！）。計算そのもの（傾きを含む）は、パソコンの中の物理的な検算で確かめてある。

### 2.4 iPhone の許可のボタン

- 「位置と方位を使う」を押すと、位置の許可と、動きと方向の許可の 2 つの確認が出るか。順番と文言。
- 許可を断ったあと、もう一度ボタンを押したときに確認が出るか（出ない場合は、設定から変える案内が要る）。
- HTTPS でないと許可が求められない。実機向けの HTTPS の配信の方法は決まっていない（`docs/proto/app.md` と同じ）。

### 2.5 Android の Chrome

- `deviceorientationabsolute` が出るか、その北が磁北か真北か（このモジュールは磁北とみなして偏角を引いている。真北なら、偏角の分（静岡県で約 7〜8 度）ずれる）。
- 確かめ方：iPhone と並べて同じ方向に向け、画面の「北から○度」を比べる。地図で方位を測った目標とも比べる。
- 機種によって、`deviceorientationabsolute` の値がない（`alpha` が空）ことがあるか。そのときは「北を基準にした向きが得られません」と出て、矢印は出ない。

### 2.6 GPS の進行方向

- 歩く速さ（1.0〜1.5m/s）で、`coords.heading` と `coords.speed` が出るか（iPhone は止まっていると出ない、などの違い）。
- 曲がり角で GPS の進行方向が遅れて、端末の方位と食い違い、矢印が一時的に消えることがあるか。消える時間が長すぎないか。
- 1.0m/s（！！仮の値！！）、60 度（！！仮の値！！）の値が妥当か。

### 2.7 位置の誤差

- 建物の中、高い建物の間で、誤差がどれくらいになるか。誤差の円の中に避難場所があるとき「方向を示せません」と出ることの分かりやすさ。
- 誤差 1000m（！！仮の値！！）を超えると「方向を示せません」になる。山間部・地下で頻繁に起きないか。

### 2.8 表示

- 屋外の日差しの下で、矢印と文字が読めるか（明るい表示）。夜（暗い表示）。
- 片手で持ったまま、親指で「この方向は通れない」と「取り消す」が押せるか。押し間違い。
- 矢印と北を上にした図を、利用者が取り違えないか（図の下に「北を上にした図です。端末の向きとは関係ありません」と出している）。
- 「直線の方向です。道順ではありません」が、矢印に従って川や崖をまっすぐ進むことを防げるか。人に見てもらう。
- 北を上にした図（点と破線、矢印とは別の色）を、矢印と取り違えないか。
- 津波のとき、最も近い避難場所が海の側にある場合に、矢印が海の方を指すことがある（モジュールは判断しない、BW-S1）。画面での注意書きを足すか、人が決める。
