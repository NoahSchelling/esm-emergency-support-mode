## 目的

秘密情報・個人情報の検査（`scripts/check-secrets.sh`、`.githooks/` の 2 つのフック、`.claude/settings.json` のフックと `scripts/claude-hook-bash.sh`）を、攻撃する側の視点で調べる。この回は**直さない**。見つけることに専念し、結果を `docs/review/check-secrets_review.md` にまとめる。各項目に、再現の手順、深刻度（高・中・低）、修正案を書く。

## 決めたこと（理由・却下した案）

- **実験は、リポジトリの外の使い捨ての複製で行った**：作業用の場所に、このリポジトリのベアの複製（偽のリモート）と、そこからの複製を作った。フックを有効にしたまま、実際にコミットとプッシュをした。
  - 理由：検査が止めるか通すかは、コミットとプッシュを実際に行わないと確かめられない。本物のリポジトリやリモートに、偽の値を含むコミットを作らないため。
  - 却下：本物のリポジトリで別ブランチを切る案。誤ってプッシュすると、偽の値でも公開の履歴に残る。
- **偽の値は、スクリプトの中で断片をつないで作った**：依頼のとおり。値を作るスクリプトは作業用の場所に置き、リポジトリには入れていない。メールアドレスの形の値には、使われない予約ドメインを使った。禁止語は架空の語にした。
- **レビュー文書には、検出パターンそのものを書かなかった**：キーの接頭辞やメールアドレスの形は、言葉で説明した。偽の値の作り方も、付録で言葉で書いた。再現の手順では、偽の値をシェルの変数名で書いた。
- **深刻度の目安を文書の最初に書いた**：「うっかりでも起きやすく、手元のフックと CI の両方をすり抜けるか」を高の基準にした。わざとでないと起きない経路は、低くした。
- **Claude Code のフックは、フックに渡るのと同じ形の JSON を作って直接試した**：Bash ツールで本当に試すと、このセッションのフックはこのリポジトリを検査するので、lab のステージの状態を使えないため。
- **GitHub の側の設定（必須の検査、Secrets の登録）は「要確認」にした**：このセッションでは GitHub の MCP に接続できず、確かめられなかったため。推測で「設定されていない」とは書かなかった。

## 試して分かったこと（失敗を含む）

- セッションの最初の状態：手元のブランチは最新の main と同じ位置だった。リモートには、このセッションのブランチ名はまだなかった。`git config core.hooksPath` は `.githooks` だった。
- 今の全履歴を CI と同じ方法で検査すると、停止 0、警告 0、約 3.7 秒だった。作成者とコミッターのメールアドレスは、ドメインだけを数えて確かめた。すべて GitHub の noreply か、Claude の共同作成者のドメインだった（アドレスそのものは表示していない）。
- 高と判断したもの（詳しくはレビュー文書）：
  - コミットメッセージ、作成者の情報、ブランチ名、タグのメッセージは、どの守りでも検査されない。
  - Git がバイナリとみなしたファイルは、中身を見ない。`.gitattributes` に 1 行書くだけでも、UTF-16 で保存しただけでもすり抜ける。CI でも同じ。
  - `--diff-filter=ACMR` に種類の変更が入っていない。シンボリックリンクを、キーを書いたファイルに置き換えると、3 つの守りすべてを通った。
  - 「ステージ＋フックを外したコミット」を 1 回のコマンドで行うと、Claude Code のフックも Git のフックも働かない。
  - フックの実行権限を外すコミットや、スクリプトの書き換えを、検査は止めない。PR の CI は、PR 側のスクリプトで動く。
- 予想していなかったこと：メールアドレスの規則で、長い行の処理時間が長さの 2 乗に比例して増えた。300KB の 1 行で約 220 秒、1MB では 300 秒で打ち切った。規則を 1 つずつ測って、原因はこの規則だと突き止めた。
- 検査の出力は、見つけた値は伏せるが、ファイル名は伏せない。禁止語を含むファイル名は、出力にそのまま出た。
- 失敗した試し：
  - 1 回目の一括の試しで、1 つのケースがディレクトリの作り直しを忘れて失敗した。作り直してやり直した。
  - あるケースの後始末が失敗し、次のケース（フックの実行権限）が汚れた状態で走った。lab を作り直して、そのケースだけやり直した。
  - 親のないコミットの試しでは、作業ツリーから検査スクリプト自体が消えていた（終了コード 127）。スクリプトを外に複製してやり直した。
  - ブランチ名を 2 つ指定したフェッチが、片方がリモートにないため全体で失敗した。main だけをフェッチし直した。
- 作業用の場所でのコマンドの中に、ヒアドキュメントとして `git commit` の文字があった。それだけで、このセッションの Claude Code のフックが反応し、このリポジトリのステージを検査した（何もステージしていないので通った）。この挙動もレビューに書いた。
- 実験が終わったあと、偽の値を含む複製とベアリポジトリを消した。
- **このセッションの個人語の検査は「未実施」だった**（環境変数 ESM_DENYLIST_FILE が未設定）。lab の中だけで、架空の語を入れた禁止語ファイルを使って、検査の挙動を試した。このリポジトリに入れた 2 つの文書には、個人の情報を書いていないことを人の目で確かめた。

## Claude の使い方（どの機能を何のために）

- **Read**：検査スクリプト、2 つのフック、Claude Code のフックの設定とスクリプト、CI のワークフロー、開発ログのひな形を読んだ。
- **Write**：lab を作るスクリプトと、ケースごとの試しのスクリプトを、作業用の場所に書いた。レビュー文書と開発ログを書いた。
- **Bash（git、iconv、gzip、bash）**：lab の中で、ケースごとにステージ、コミット、プッシュを行い、止めたか通したかを記録した。処理時間も測った。
- **Bash（python3 を分離モードで）**：Claude Code のフックに渡る JSON を作り、`claude-hook-bash.sh` に直接渡した。
- **Claude Code のフック（PreToolUse）**：コミットとプッシュのときに、検査が走ることを確かめた。この回の作業で、意図しない反応（ヒアドキュメントの中の文字への反応）も観察した。
- サブエージェントは使っていない。

## l4b へ戻す学び

- 「二重の守り」「三重の守り」は、それぞれの守りが**別々の経路**を見ているときにだけ効く。今回は、3 つの守りが同じ前提（差分の `+` の行だけを、種類を絞って見る）を共有していた。そのため、バイナリ扱いや種類の変更は、3 つを同時にすり抜けた。
- 守りを止める操作（フックの場所の変更、`--no-verify`、実行権限、スクリプトの書き換え）は、検査の対象そのものにしないと、運用の約束だけが頼りになる。
- 正規表現による検査は、誤検出だけでなく「遅さ」でも運用を壊しうる。遅い検査は外される。
