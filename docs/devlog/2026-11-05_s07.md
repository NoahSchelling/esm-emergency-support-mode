# 2026-11-05 s07

## 目的

緊急支援モードの状態（平常／警戒高め／緊急と、緊急の中の段階）を切り替える状態機械を `modules/mode/` に作る。入力は公的な発表と利用者の申告と時間の経過だけにし、独自の判断はしない。規則 1〜7 のテストを作り、サブエージェントに規則と実装を独立に突き合わせさせ、食い違いを直す。

## 決めたこと（理由・却下した案）

- **状態の更新は `step(前の状態, イベント, { config })` の 1 つの関数にした。** 前の状態は書き換えず、凍結した新しい状態を返す。同じ入力には同じ結果を返す。返すのは、新しい状態・共通の形の結果・記録の 3 つ。記録は状態の中にためない（状態が大きくなり続けるため）。保存は呼び出す側に任せる。
- **発表の強い・弱い・下限は、`categories.js` の固定の表で引く。** 発表の中身から危険度を推定しない（BW-S1）。震度は値の大小だけを見る（3 以上で弱い、6弱以上で下限）。表にない種類と読めない震度は `unknown` を返し、モードを変えない（BW-S3）。
- **段階は名前だけを返す。** 心理的な対応・医療の助言のための差し込み口として `supportFor()` だけを置いた。いつも `unsupported` を返す（BW-S4）。
- **段階の時間の既定値は仮の値にした。** 15 分、6 時間、3 日、2 週間、90 日、365 日。段階の説明の時間の目安から置いただけで、根拠はない。コード・README・結果の文面に「！！仮の値！！」と書いた。
- **6 段階と 7 段階の両方を扱えるようにした。** 段階の名前の配列と時間の配列を設定で渡せる。6 段階案の中身は決まっていないので、6 段階の既定値は作らなかった（勝手に段階をまとめないため）。
- **規則どうしの衝突は `docs/proto/mode.md` に両論を書いた。** 実装では、変えやすいものを設定にした。次の 4 点は人が決める（既定値は仮の値）。
  - 解除で緊急から下げるか（`onEndInEmergency`）。
  - 震度の下限をいつまで保つか（`intensityFloorHours`）。
  - 「緊急にしない」を、その場で一度効く申告とするか、取り消すまで続く申告とするか。
  - 震度6弱以上の観測を強い発表に入れるか。
- **下限があるときの「平常に戻して」は、全部断る（`denied`）。** 「警戒高めまでは下げる」とは読まなかった。頼まれたことと違う結果を黙って返すことになるため。両論は `mode.md` の 7 章に書いた。
- **却下した案：「緊急にしない」を、そのあとの強い発表も止める設定として残す案。** 規則 1 の「自動で緊急に移る」を利用者が止められてしまうため。

## 試して分かったこと（失敗を含む）

- `node --test modules/mode/test/` のように、ディレクトリを指定するとテストを見つけられなかった（Node.js 22 では、ディレクトリを 1 つのモジュールとして読もうとする）。`node --test 'modules/mode/test/*.test.js'` とパターンで渡すと動いた。
- 最初の実装でテストは 58 件すべて通った。それでも独立した突き合わせで、中くらいの不具合が 3 件、軽い不具合が 4 件見つかった。テストが通ることと、規則に合っていることは別だった。
  - 中：段階が `tick`（時間の経過）のときにしか進まない。発表や申告のイベントでは、古い段階のまま返る。
  - 中：期間が過ぎた震度の下限が、`tick` が来るまで申告を止め続ける。
  - 中：前の状態の発表の一覧に不正な項目があると、`error` を返さずに例外が出る。`createConfig` を通さない設定も検査していない。
  - 軽：同じ `id` で種類が違う続報（警報から大津波警報へ）を「受け済み」として捨て、下限が付かない。
  - 軽：時刻の古い `tick` を `ok` で返す。対象の発表より前の時刻の解除を受け付ける。
  - 軽：公的発表に `source: "user"` を付けても通る。
  - 軽：2 月 30 日のような存在しない日付を受け付ける。
- 直したこと：時間の経過による変化（段階、下限の期間）を、どのイベントでもその時刻で先に当てはめるようにした。ほかの不具合もすべて直し、それぞれに再発防止のテストを足した（計 67 件、すべて通る）。サブエージェントが残した確認用のスクリプトを直したあとに動かし直し、指摘の場面がどれも直っていることを確かめた。
- 段階の進め方を変えたので、解除のテストで記録の並びが変わった（解除の前に段階 2 への記録が入る）。仕様の変更による変化なので、テストのほうを直した。
- **個人語の検査は未実施。** 環境変数 `ESM_DENYLIST_FILE` が未設定で、フックがそのことを表示した。

## Claude の使い方（どの機能を何のために）

- **サブエージェント（general-purpose）1 体**：規則と実装の独立した突き合わせ。依頼の規則・入力・守ること・共通の結果の形を原文のまま渡した。次の 3 つを頼んだ。
  - 規則を先に読み、自分の期待を作ってからコードを読むこと。
  - 規則ごとに「合う／合わない／あいまい」を、根拠（行番号か、確認用スクリプトの入力と出力）付きで出すこと。
  - 規則どうしの衝突と、規則が何も言っていない場面を挙げること。

  ファイルは書き換えさせず、確認用のスクリプトはスクラッチパッドにだけ置かせた。結果は上の「試して分かったこと」のとおり。あいまいとされた点（規則 3 と規則 4 の範囲、余震での段階のやり直し）は、直さずに `mode.md` に書いた。
- **Claude Code のフック**：コミットとプッシュのたびに検査が走った（止められた変更はない）。
- サブエージェントの突き合わせを待つあいだに、README と `mode.md` を書いた。

## l4b へ戻す学び

- 時間で変わる状態は、「時間のイベントを受けたとき」ではなく「どのイベントでも、その時刻で」計算しておく。そうしないと、表示が古いままになる。
- 「同じ id なら重複」という判定は、内容の引き上げを落とす。重複は id と中身の両方で判定する。
- テストを書いた本人とは別に、規則を先に読んだ別の目で突き合わせると、テストの抜けが見つかる。
