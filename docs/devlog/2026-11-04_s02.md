# 2026-11-04 s02

## 目的

緊急支援の試作で使う、気象庁の公的データの取得方法と利用条件を調べ、`docs/research/jma_data.md` にまとめる。対象は次の 3 つ。

- 防災情報 XML の Atom フィード
- 地震情報と気象警報の XML 電文
- 気象庁ホームページの内部の JSON

実物を取得して確かめ、小さいサンプルを `data/samples/` に 3 件まで保存する。

追加の依頼（同じセッション）：電文ごとの解説資料を読んで、残っていた未確認事項を確かめる。

追加の依頼 2（同じセッション、PR マージ後）：利用者が `www.digital.go.jp` を許可したので、公共データ利用規約（第 1.0 版）の条文を確かめる。

## 決めたこと（理由・却下した案）

- **調査メモは「確認済み（文書）／確認済み（取得）／未確認」に分けて書く。** 推測と事実を混ぜないという依頼に合わせた。1 回の取得で見たことは「いつもそうなるとは限らない」と書いた。
- **最初の回で書いた「手掛かり（検索結果の要約）」と「Claude の事前知識」は、取得できた後にすべて外した。** 公式の文書と実物で確かめた内容に置き換えた。確かめられなかったものは「未確認」に残した。
- **サンプルは次の 3 件にした。**
  - 地震情報：小さい（約 2KB）。
  - 気象警報：「注意報を解除します。」の電文。「解除」と「発表警報・注意報はなし」の両方の実例になる。
  - 地震火山の Atom フィード：フィードの構造の例。
  - 却下：内部 JSON をサンプルにする案。仕様書がなく、形が変わる恐れがあるため。
- **サンプルは加工せずに保存し、出典を `data/samples/README.md` と `README.md` に書いた。** CLAUDE.md の「外部データの出典を README に明記する」に合わせた。README には出典の欄だけを足した。BW-S2 の記載（公的情報を優先すること）はこの回の範囲外として、まだ書いていない。
- 安全の下限にかかわる点を、調査メモに書いた。
  - `Control/Status` が「通常」以外（訓練・試験）の電文は画面に出さない（BW-S1）。
  - 「解除」「発表警報・注意報はなし」を「安全」と表示しない（BW-S3）。
  - 警報の値は言い換えない。編集・加工したら「加工して作成」と書く（気象業務法第 17 条・第 23 条、XML 留意事項）。

- **（追加の依頼）警報は R06 形式を使う、と調査メモに書いた。**
  - 理由：旧形式の解説には「危険警報」が出てこない。旧形式だけ読むとレベル 4 を見落とす恐れがある。
  - まだ実装はしていない。旧形式の終了時期は見つけられなかった。
- **（追加の依頼）地震情報の「訂正」は、資料の間で書き方が違うので「未確認」のまま残した。**
  - 地震火山解説は「訂正」を挙げ、運用整理表は「発表／取消」だけを挙げている。
  - どちらかに寄せて書くことはしなかった。受け取る側は両方を処理できるように作る、と書いた。
- **（追加の依頼）サンプルは 3 件のまま増やさなかった。** 依頼の上限が 3 件のため。公式サンプルや R06 電文は、ファイル名と URL を調査メモに書いて参照する形にした。

- **（追加の依頼 2）出典は、規約の一般的な例（「PDL1.0（規約原文ページの URL）」まで書く形）ではなく、気象庁の記載例を使う。**
  - 規約 1.1 に、提供者が「重要情報」で記載例を示しているときはそちらを参考にする、とあるため。
- **（追加の依頼 2）前の PR がマージ済みだったので、作業ブランチを最新の main から作り直した。**

## 試して分かったこと（失敗を含む）

- セッションの最初に `git config core.hooksPath` を表示した。値は `.githooks` だった。2 回目の依頼のときも同じだった。
- **1 回目：気象庁のサイトに接続できなかった。** このクラウド実行環境のネットワーク設定で、`www.data.jma.go.jp`・`www.jma.go.jp`・`xml.kishou.go.jp` への接続がプロキシに拒否された（CONNECT に 403）。WebFetch でも名前解決できなかった。
  - 調査メモは「ほぼすべて未確認」の版でコミットした。
  - 利用者にドメインの許可を頼んだ。
- **2 回目：利用者が許可を変えた後、すべて取得できた。** 分かった主なこと：
  - フィードは高頻度（毎分更新）と長期（毎時更新）の 2 系統で、それぞれ 4 分類（定時・随時・地震火山・その他）。8 本とも取得できた。
  - フィードにも電文にも `Access-Control-Allow-Origin: *` が付いていた。内部 JSON も同じだった。
    - Chromium で別オリジンの画面から `fetch` して、実際に読めることも確かめた。
    - 確かめた画面のオリジンは `http://127.0.0.1:8765`。プロキシを通している。
  - 条件付き取得（ETag と If-Modified-Since）で 304 が返った。
  - 取消・訂正は `Head/InfoType` で表す。有効な電文は `Control/DateTime` が最も新しいもので、`Serial` の順ではない（運用指針）。
  - 解除は電文の種類ではなく、地域ごとの `Kind/Status` で表す。実物で確かめた。
  - **内部 JSON の古い場所（`bosai/warning/data/warning/`）が、2026-05-28 で更新が止まったデータを 200 で返していた。** 新しい場所（`bosai/warning/data/r8/`）は最新だった。仕様書のないデータが黙って古くなる実例で、BW-S3 の観点で危ない。
  - 電文 XML の応答は CDN のキャッシュから返ることがあり、`Date` ヘッダは取得した時刻と一致しなかった。サンプルの取得日時は、そのことを書いたうえで記録した。
  - 訂正・取消の電文の実物は見つけられなかった。Atom フィードの `entry` には `InfoType` が出ないため。
  - 津波の電文も、この 7 日分のフィードには無かった。
- **このセッションの個人語の検査は「未実施」だった**（環境変数 ESM_DENYLIST_FILE が未設定）。個人語の確認は人の目に頼った。
  - サンプルの電文には、地名と震度観測点の名前（公的な観測点）が入っているが、個人の情報は入っていない。
  - 気象庁の問い合わせ先のメールアドレスと電話番号は、取得したページに載っていたが、文書には写していない。

- **（追加の依頼）解説資料セットと公式サンプルを読んだ。** 解説資料セットは約 13MB、公式サンプルは約 4MB の zip。
  - zip のファイル名が文字化けしたので、Python の標準ライブラリで名前を直して展開した。展開先は空のディレクトリにした。
  - 警報の `Kind/Status` が取る値の一覧と、`ChangeStatus`・`FullStatus`・`EditingMark` の定義が分かった。
  - 警報の `InfoType` は「発表／訂正」だけで、取消が無い。
  - 地震・津波の取消は電文の種類ごとに出る。取消電文の `Body` は `Text` だけ。公式サンプルでも確かめた。
  - 津波の解除は「解除」という名前では表さない。`Kind`（今回）と `LastKind`（前回）の組で表す。
  - R06 形式は令和 8 年度出水期から提供と告知されていた。
  - 同じ「乾燥注意報の解除」が、R06 と旧形式の両方で同じ時刻に出ていることも、実物で確かめた。
  - 旧形式の提供終了の時期は、令和 7〜8 年度の更新のお知らせ（約 50 件）を探しても見つからなかった。
  - 公共データ利用規約（第 1.0 版）は、置き場所の `www.digital.go.jp` がネットワーク設定で拒否されて読めなかった。拒否された後は試し直していない。
  - 個人語の検査は、この追加の回も「未実施」だった（ESM_DENYLIST_FILE が未設定）。

- **（追加の依頼 2）規約の条文で分かったこと：**
  - 数値データや簡単な表は、著作権の保護の対象外で、規約の適用もない。ただし、気象業務法の制約は別に残る。
  - 編集・加工したときは、加工したことに加えて「主体」も書く。
  - 編集・加工したものを、国が作った未加工のもののように見せてはいけない。

## Claude の使い方（どの機能を何のために）

- **Bash（curl）：** フィード・電文・内部 JSON・公式の文書（HTML と PDF）を取得し、応答ヘッダを記録した。PDF は pdftotext で文字にして読んだ。
- **Python（標準ライブラリだけ）：** フィードの `entry` を種類ごとに数えた。スクリプトはスクラッチの場所に置き、取得したファイルとは別のディレクトリにした。
- **Playwright（Chromium）：** 別オリジンの画面から実際に `fetch` できるかを確かめた（CORS の確認）。
- **環境のドキュメントを読む機能：** 1 回目にホストが拒否されたとき、利用者がどこで設定を変えるかを確かめた。
- **WebSearch：** 1 回目に手掛かりを集めた。2 回目にはその内容をすべて公式の文書で確かめ直し、検索だけを根拠にした記述は残していない。
- **Hooks：** コミットのときに秘密情報・個人情報の検査が自動で走る。

- **（追加の依頼）PDF 一覧の取得：** 更新のお知らせの PDF をまとめて取得するコマンドが 2 分の時間制限を超え、バックグラウンドに回った。終わるのを待ってから結果を読んだ。
- **（追加の依頼）pdftotext：** 表の段組みが崩れるので、表から読んだ値は解説資料の本文と照らし合わせた。

- **（追加の依頼 2）** curl で規約のページを取得した。HTML から本文を取り出すのに、Python の標準ライブラリを使った。

## 誤り記録

- サンプルの説明で、地震情報の `Date` ヘッダが古い理由を最初は「CDN のキャッシュだろう（推測）」と書いた。そのあと応答ヘッダ（`x-cache` と `age`）を見て確かめ、事実として書き直した。推測で書く前にヘッダを見ればよかった。
- 調査メモの初稿に「インターネット上の解説記事でよく紹介されている場所」という、確かめていない言い回しが入っていた。見直しで気づいて消した。

- （追加の依頼）バックグラウンドの取得の結果を読むとき、カレントディレクトリが戻っていたため、`*.txt` が展開されずに空振りした。絶対パスで指定し直した。
- （追加の依頼）調査メモに書いた津波サンプルの引用で、本文にある言葉を「付加文にある」と書いていた。見直しで原文と照らし合わせて直した。

- （追加の依頼 2）なし。

## l4b へ戻す学び

- 調査の依頼では、最初に「対象のサイトに接続できるか」を 1 回だけ確かめる。接続できなければ、別のホストを試し続けずに利用者に設定を頼む。
- 仕様書のないデータは、壊れるときにエラーにならないことがある（古いデータが 200 で返る）。発表時刻を必ず見て、古いものを「今の状態」として出さない。
- 「解除」「発表警報・注意報はなし」は、公的な電文の中の言葉としてそのまま出す。「安全」に言い換えない。

- 同じ情報が複数の形式で並んで出ているときは、新しい形式の解説資料で、古い形式に無い区分（ここでは危険警報）を確かめる。
- 資料の間で書き方が違うときは、どちらかに寄せず、両方を書いて「未確認」にする。実装は両方に耐えるように作る。
