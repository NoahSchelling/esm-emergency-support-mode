## 決めたこと（理由・却下した案）

- **調査メモは「確認済み（文書）／確認済み（取得）／未確認」に分けて書く。** 推測と事実を混ぜないという依頼に合わせた。1 回の取得で見たことは「いつもそうなるとは限らない」と書いた。
- **最初の回で書いた「手掛かり（検索結果の要約）」と「Claude の事前知識」は、取得できた後にすべて外した。** 公式の文書と実物で確かめた内容に置き換えた。確かめられなかったものは「未確認」に残した。
- **サンプルは次の 3 件にした。**
  - 地震情報：小さい（約 2KB）。
  - 気象警報：「注意報を解除します。」の電文。「解除」と「発表警報・注意報はなし」の両方の実例になる。
  - 地震火山の Atom フィード：フィードの構造の例。
  - 却下：内部 JSON をサンプルにする案。仕様書がなく、形が変わる恐れがあるため。
- **サンプルは加工せずに保存し、出典を `data/samples/README.md` と `README.md` に書いた。** CLAUDE.md の「外部データの出典を README に明記する」に合わせた。README には出典の欄だけを足した。BW-S2 の記載（公的情報を優先すること）はこの回の範囲外として、まだ書いていない。
- 安全の下限にかかわる点を、調査メモに書いた。
  - `Control/Status` が「通常」以外（訓練・試験）の電文は画面に出さない（BW-S1）。
  - 「解除」「発表警報・注意報はなし」を「安全」と表示しない（BW-S3）。
  - 警報の値は言い換えない。編集・加工したら「加工して作成」と書く（気象業務法第 17 条・第 23 条、XML 留意事項）。

- **（追加の依頼）警報は R06 形式を使う、と調査メモに書いた。**
  - 理由：旧形式の解説には「危険警報」が出てこない。旧形式だけ読むとレベル 4 を見落とす恐れがある。

- **（追加の依頼）地震情報の「訂正」は、資料の間で書き方が違うので「未確認」のまま残した。**
  - 地震火山解説は「訂正」を挙げ、運用整理表は「発表／取消」だけを挙げている。
  - どちらかに寄せて書くことはしなかった。受け取る側は両方を処理できるように作る、と書いた。
- **（追加の依頼）サンプルは 3 件のまま増やさなかった。** 依頼の上限が 3 件のため。公式サンプルや R06 電文は、ファイル名と URL を調査メモに書いて参照する形にした。

- **（追加の依頼 2）出典は、規約の一般的な例（「PDL1.0（規約原文ページの URL）」まで書く形）ではなく、気象庁の記載例を使う。**
  - 規約 1.1 に、提供者が「重要情報」で記載例を示しているときはそちらを参考にする、とあるため。
- **（追加の依頼 2）前の PR がマージ済みだったので、作業ブランチを最新の main から作り直した。**

- **（追加の依頼 4）GitHub Actions で、手元と同じ `scripts/check-secrets.sh` を走らせる。** 検査の中身を 2 つに分けないため。
  - 走るとき：PR の作成と更新のたび（GitHub の画面での衝突の解消も、PR のブランチへのコミットになるので含まれる）、main への push のたび。

- **（追加の依頼 4）検査スクリプトに `--range <基点> <先端>` を足した。**
  - 理由：GitHub の実行環境では、検査するコミットがすでにリモートにある。そのため、既存の `--push`（リモートにないコミットを検査）では何も検査されない。

  - 新しいブランチや強制プッシュで、push の前の先端が使えないときは、全履歴を検査する（すべて 0 の基点）。検査できないときに通さない方針どおり。

- **（追加の依頼 5）名前は `2026-11-04_s02_pre-push.md` にした。**

## Claude の使い方（どの機能を何のために）

- **Bash（curl）：** フィード・電文・内部 JSON・公式の文書（HTML と PDF）を取得し、応答ヘッダを記録した。PDF は pdftotext で文字にして読んだ。
- **Python（標準ライブラリだけ）：** フィードの `entry` を種類ごとに数えた。スクリプトはスクラッチの場所に置き、取得したファイルとは別のディレクトリにした。
- **Playwright（Chromium）：** 別オリジンの画面から実際に `fetch` できるかを確かめた（CORS の確認）。
- **環境のドキュメントを読む機能：** 1 回目にホストが拒否されたとき、利用者がどこで設定を変えるかを確かめた。
- **WebSearch：** 1 回目に手掛かりを集めた。2 回目にはその内容をすべて公式の文書で確かめ直し、検索だけを根拠にした記述は残していない。
- **Hooks：** コミットのときに秘密情報・個人情報の検査が自動で走る。

- **（追加の依頼）PDF 一覧の取得：** 更新のお知らせの PDF をまとめて取得するコマンドが 2 分の時間制限を超え、バックグラウンドに回った。終わるのを待ってから結果を読んだ。
- **（追加の依頼）pdftotext：** 表の段組みが崩れるので、表から読んだ値は解説資料の本文と照らし合わせた。

- **（追加の依頼 2）** curl で規約のページを取得した。HTML から本文を取り出すのに、Python の標準ライブラリを使った。

## l4b へ戻す学び

- 調査の依頼では、最初に「対象のサイトに接続できるか」を 1 回だけ確かめる。接続できなければ、別のホストを試し続けずに利用者に設定を頼む。
- 仕様書のないデータは、壊れるときにエラーにならないことがある（古いデータが 200 で返る）。発表時刻を必ず見て、古いものを「今の状態」として出さない。
- 「解除」「発表警報・注意報はなし」は、公的な電文の中の言葉としてそのまま出す。「安全」に言い換えない。

- 同じ情報が複数の形式で並んで出ているときは、新しい形式の解説資料で、古い形式に無い区分（ここでは危険警報）を確かめる。
- 資料の間で書き方が違うときは、どちらかに寄せず、両方を書いて「未確認」にする。実装は両方に耐えるように作る。

- 手元のフックは、GitHub の画面での編集を検査できない。秘密情報の検査は、CI（PR ごとの自動の検査）でも走らせて重ねる。
- 調査で決めたこと（使う形式、訓練・試験の扱い、取消の扱い）は、試作に反映されたかを見直しの観点に入れる。

- 手元の検査を CI でも走らせるときは、「リモートにないもの」のような手元の前提が、CI の環境で成り立つかを確かめる。

- 開発ログの番号（sNN）は回ごとに一つ。別の回のログを動かすときは、新しい番号を取らずに、動かした回と中身が分かる名前にする。

- 外部のアクションの版を上げるときは、実行環境（node24 など）を action.yml で確かめ、間の変更履歴から自分の設定に関係する変更だけを拾う。
