## 決めたこと（理由・却下した案）

- **「常に回す」の範囲は人に確かめた**：方位の精度を確かめられないとき（Android は精度の値を出さないので、立ち止まっている間やデモではほぼこの状態）にも回すかを聞き、「確かめたときだけ回す」に決まった。間違った方向を指すくらいなら回さない、という s05 までの判断を変えない。そのため、Android で立ち止まっている間とデモでは、北が上の図のままになる。README の「既知の限界」にも書いた。
- **回し方**：画面全体の描き直しは 1 秒ごとのまま。方位の図だけ、0.1 秒ごとに最新の向きを読み、0.3 秒の滑らかな動きで回す。続けて回すのは、直前の描き直しで `modules/evac/` が向きを認めたとき（または避難目標がなく向きが分かるとき）だけ。避難目標の印の向きは、認められた避難場所の方位から、その時点の向きで計算し直す（`screenArrowDeg`）。却下した案：毎回 `computeEvacDirections` を呼び直す（重く、1 秒ごとの判定で足りる）。
- **× の位置**：除外した方向（真北からの方位）に、方位の円の一部として置く。円と一緒に回り、× の形は崩れないよう逆に回して正立させる。
- **「▶現在通れない方向」は常に出す**：除外がないときは「ありません。」。「通れるかどうかは、あなたの判断です」と「10 分たつと自動で取り消します」は、開いた中に小さく置いた。
- **トグルスイッチと「入力欄なし」の決まり**：避難者の画面には入力欄を置かない決まりがある。スイッチは文字を打つ欄ではないので、テストを「文字を打つ欄なし、入力はスイッチ 1 つだけ」に直した。
- **知らせ**：同じ文の知らせが続いたときは、時間を延ばすだけにする（重ねて出さない）。閉じるボタンはなくした（2 秒で閉じるため）。「発表がなくなった」ときも「情報が更新されました」だけにした。
- **観測値の知らせ**：観測を入れたときと入れないときの外枠のレベルを比べ、観測で上がったとき（上がり始めと、さらに上がったとき）だけ出す。
- **地図のリンク**：`https://maps.gsi.go.jp/#15/緯度/経度/`（小数 6 桁）。避難場所の座標は公開されたデータで、いる場所は含まない。
- **ついでに直したこと**：同意のやめ方の文が「同意をやめる」を押す、のままだった（s05 でラジオボタンにした後の残り）。「同意しない」を選ぶ、に直した。

## 追記：デバッグと、本物の災害での表示の検証

人からの依頼：

- デモモード静岡県：途中から方位表示が古いバージョンになる。
- デモモード福島県：途中から外枠表示が消える。
- 「津波は予想より高くなる場合あり。」は、津波に関する情報が出ているときだけ出す。
- 本物の災害でも正しく表示されるか、コードを検証する。

分かったことと直したこと：

- **静岡県の「古いバージョン」**：古いファイルではなく、北が上の図への切り替えだった。津波警報（3 段目）で避難目標が出ると、方位を確かめられない端末（Android は精度の値を出さない。デモでは位置が固定なので GPS の進行方向との照合もできない）では、北が上の図（点と点線、▲ なし）になる。2 段目までは避難目標がないので、向きが分かれば円が回る。これが「途中から古い表示」に見えた。
  - 安全の判断（確かめた向きでだけ回す）は変えない。
  - 図の下に「北が上の図です（方位を確かめられないため）。」を常に見える形で出す（折り畳まない）。Android で照合待ちのときは「スマートフォンの上を進む方向に向けて少し歩くと、回る図に戻ります。」を足す。
  - デモでも、端末そのものの GPS の進行方向で方位を確かめられるようにした（位置はデモの地点のまま）。歩けば回る図に戻る。
- **福島県の外枠**：一段ずつと実時間の再生で調べると、外枠は最後の「津波注意報の解除」まで消えていなかった。ただし次の 2 つがおかしかった。
  - 解除の後も、一行の情報のいちばん上に「津波 9.3m以上、相馬、実測」が残っていた。外枠は消えたのに津波の行が残るので、「外枠だけが消えた」ように見える。
  - 3 月 12 日 20:20 に津波警報（津波）に下がった後も、前日の観測（9.3m以上）で外枠が紫のままだった。
  - 直し方：観測値は「その区域に津波の発表が出ていて、その発表より後に観測されたもの」だけを使う（`app/shell/live.js` の `currentFacts`）。気象庁が観測を踏まえて警報を下げた後は、古い観測で外枠を上げない。観測は外枠を上げるだけ、という決まりは変えない。福島県の外枠は 紫→紫→紫→紫→紫→赤→黄→なし になった。
  - 実時間の再生で、外枠が紫・速い点滅（1 秒周期の点滅で、半分の時間は外枠が消える）になることも確かめた。これが「消える」に見えた可能性もある。
- **注意書き**：津波の発表が出ている、または予想・観測の高さがあるときだけ出す。
- **本物の電文での検証（コードを読んで見つけた問題）**：
  - **津波警報が数分で外枠から消えるおそれ（重大）**：画面は C-A の `recent`（両方のフィードを合わせた新しい 10 件）だけを読んでいた。実データの随時フィードは 283 件あり、ほかの県の警報も次々に流れる。津波警報が 10 件の外に出ると、まだ出ているのに外枠が消え、「身の安全を確保してください」になる。C-A に `current`（同じ種類・同じ発表元のいちばん新しい電文を持ち続ける）を足し、画面はそれを使うようにした。
  - **ほかの県の警報で、自分の県の警報が上書きされるおそれ**：画面は「電文の種類名ごとにいちばん新しいもの」だけを使っていた。気象警報はどの県でも同じ種類名なので、ほかの県の電文が来ると自分の県の警報が消える。発表元（気象台）ごとに分けた。
  - **詳細の取得が追いつかないおそれ**：C-A は 1 回（60 秒）に詳細を 5 件しか読まなかった。新しい順に読むので、混み合う日には津波の電文が後回しになる。20 件にし、津波・警報を先に読むようにした。
  - **津波の解除と予報の扱い**：気象庁の電文の種類名には「警報解除」「津波注意報解除」「津波なし」「津波予報（若干の海面変動）」がある。予想の高さと津波警報の判定で、これらを「出ている」と数えないようにした（`isTsunamiAnnouncement`）。
  - 確かめていないこと：本物の津波の電文（VTSE41・VTSE51）の実物で、`current` のまとめ方（津波の電文をひとまとめにする）が正しいか。津波情報が各区域の警報の種類を必ず含むかは、電文の実物で確かめる必要がある。
- テスト：アプリ 107 件、外枠のモジュール 11 件、C-A 17 件、すべて通った。

## 追記：README の「簡易な動作検証方法」

人からの依頼：審査員が第三者のスマートフォンですぐ試せるように、方法だけを README に書く（例：Amazon EC2）。

- 決めたこと：入口を 2 つにした。デモは静的な公開先（GitHub Pages など）で足りる。本物の発表を受け取るときだけ、サーバー（EC2 と Caddy と自分のドメイン）に置く。スマートフォンは HTTPS でないと位置と方位を渡さないため、HTTPS を前提に書いた。試作 C-A は 127.0.0.1 のままにし、`--demo`（模擬の警報を入れられる）は付けないと書いた。README には実際の URL を書かず、置き場所だけにした（ドメインの登録情報から個人情報がたどれることがあるため）。
- 却下した案：AWS Elastic Beanstalk。既定のアドレスが HTTPS でなく、HTTPS にはロードバランサー（固定費）か手作業の証明書が要る。Node と Python の 2 つを動かすには Docker の設定も要るため、EC2 より手軽にならない。
- 確かめたこと：リポジトリを静的なサーバーの下位のパス（GitHub Pages のプロジェクトのサイトと同じ形）で開き、福島県のデモが動くこと（外枠 5 まで）と、デモでないときは「受け取れていません」と「模擬データ」になることを確かめた。`/api/ca/status` は 404 になるが、画面は止まらない。
- 確かめていないこと：実際の GitHub Pages と EC2 での公開、Caddy の設定。

## Claude の使い方（どの機能を何のために）

- AskUserQuestion：「常に回す」が安全の判断（確かめていない向きでは回さない）とぶつかるため、人に決めてもらった。
- Playwright（手元の Chrome）：ブラウザのテストと、観測値の知らせの確かめ（ブラウザの中だけでデモを書き換える）。
- 編集は、短い Python の置き換えスクリプト（置き換え前の文が 1 か所だけあることを確かめてから置き換える）。

## l4b へ戻す学び

- 「常に〇〇する」という見た目の依頼が、安全のための例外とぶつかることがある。実装の前に、例外を残すかを人に確かめると手戻りがない。
- 重要な情報を出す場所が決まったら、知らせは「変わった」ことだけを伝えると、同じ情報が二重に出ない。

## 追記：静岡県のデモで北が上の図に戻る問題（2 回目）と、デモの間隔

人からの依頼：静岡県のデモの途中で、方位の表示がまだノースアップ（古い表示）になる。すべてのデモで、イベントの間を 1 秒ずつ長くする。

- 原因は 2 つあった。
  - Android（方位の精度の値がない）では、歩いて GPS の進行方向と照らし合わせるまで矢印を出さない。デモの位置は固定なので、立ち止まったままでは確かめられず、避難目標が出る 3 段目から北が上の図になっていた。前回は説明の文を足しただけだった。
  - スマートフォンを回している間とその後の約 1 秒は、向きの値のばらつきが 20 度を超え、安定の確かめ（`tracker.read()`）が通らない。そのたびに 1 秒ごとの描き直しが北が上の図に切り替わり、止まると回る図に戻っていた。iPhone でも起きる。
- 直し方：
  - デモのときだけ、精度の値がない向きの照らし合わせを省く（`requireConfirmationWhenAccuracyUnknown: false`）。デモの位置は固定の地点で、矢印が人を導くことはないため。本物の位置で使うときは、これまでどおり確かめる（「確かめたときだけ回す」は変えない）。
  - 回している間：最後に `tracker.read()` が向きを認めてから 4 秒（！！仮の値！！）までは、同じセンサーの最新の値（0.5 秒以内のもの）を使う。センサーが止まったとき、長く回し続けたときは、これまでどおり北が上の図になる。向きの確かめ（Android の照らし合わせ、古さ、傾き）はこの値にもそのままかかる。
- デモの間隔：静岡県 8→9 秒、福島県 6→7 秒、千葉県 7→8 秒、東京都 6→7 秒（`app/shell/demos.js`）。
- 確かめたこと：ブラウザで Android と同じ形の向きの値を毎秒 20 回入れ、静岡県のデモで、立ち止まって回る図、120 度／秒で 2.5 秒回しても回る図のまま、6 秒回すと北が上の図、止まると回る図、センサーが止まると北が上の図、を確かめた（テストに追加）。アプリのテスト 108 件がすべて通った。
- 確かめていないこと：実機（Android、iPhone）での動き。
