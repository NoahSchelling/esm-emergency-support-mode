# 2026-11-05 s05

## 目的

発災直後に利用者が打つ短い断片的な入力（例：`0846 M5.5 d50km 最大5弱`）から、時刻・震源の地名・規模・深さ・震度・地域名・問いを取り出すモジュールを `modules/fragment/` に作る。解析だけをして、助言や危険度の判断はしない。見逃しうる誤りの種類を `docs/proto/fragment.md` に書く。

## 決めたこと（理由・却下した案）

- **結果の中身は `readings`（候補の配列）にした。** 読み方が 2 通り以上ありうるとき、どれかに決めないため。ひとつの項目に 1 つの値を入れる形だと、`5弱` のときに決めることになる。曖昧でない入力も候補 1 件の配列で返し、使う側の扱いをそろえた。
- **印のない数字は読まない。** `50` や `5.5` だけでは、深さか規模か時刻かが分からない。推測で埋めるより `unknown` にする方が、BW-S3（読めないものを読めたことにしない）に合う。`d50` のように印があって単位だけない場合は、km と読み、`unitAssumed: true` と `detail` で推定と示す。
- **`5弱` などは震度と規模の両方を候補にした。** 依頼の例どおり。`M7.4 5弱` のように別に規模があるときは、規模が 2 つになる読みを外し、外したことを `detail` に出す。
- **地名の手掛かりは、都道府県名と語尾（沖・灘・部・半島など）の一覧にした。** 地名の辞書は持たない（持ち込みデータが増えて出典の管理も要る）。そのため見逃しは出る（`docs/proto/fragment.md` の 3.2）。
- **地名の役割（震源か地域名か）は手掛かりで決める。** 海の名前は震源だけ、`震源` の語があれば震源、`震度` の隣は地域名。手掛かりがなければ両方を候補にする。「震度の隣は地域名」は決め打ちなので、見逃しうる誤りに書いた。
- **「？」の前の項目は申告にしない。** `M7.4?` は規模の申告ではなく問い。`question.texts` に残し、項目には入れない。
- **日付がないときは今日とみなし、`dateBasis` と `detail` に推定と書く。** 今日とすると現在より先になる時刻は、昨日かもしれないので日付を決めない（`unresolved`）。読めない日付を書いたときは、今日で埋めない。
- **入力は 200 文字まで（`unsupported`）、候補は 16 件まで（超えたら `unknown`）。** 断片用のモジュールで、候補が爆発する入力を黙って切り捨てないため。
- **`source` は既定で `"user"`。** 模擬・再生のときだけ `options.simulated` で `"simulated"` にする。結果の `value.officiallyConfirmed` は常に `false` で、公的に確認された情報ではないことを結果の中で区別した。
- **Node.js 用に `modules/fragment/package.json`（`"type": "module"`）を置いた。** ブラウザ専用の部分は作っていない（必要なかった）。ソースが Node.js やブラウザ専用の API を使っていないことを、テストで確かめる。
- **却下：助言の入口（インターフェース）をこの回で作ること。** 依頼が「この回は解析だけ」と明記しているため。BW-S4 の「将来の追加に備えたインターフェース」は、次の回以降で作る。README には、このモジュールが助言の処理を持たないことだけ書いた。
- **却下：誤字の自動訂正。** `震ど4` を `震度4` と直すと、入力にない事実を足すことになる。読まずに `unrecognized` に残す。

## 試して分かったこと（失敗を含む）

- テスト 43 件が通る（`node --test modules/fragment/test/*.test.js`、Node.js 22）。
- **`node --test` にディレクトリを渡すと失敗する**（Node.js 22 ではモジュールとして探しに行く）。ファイルの glob を渡す形にして、README に書いた。
- **最初のテストで 2 件が落ちた。** 1 件はテストの期待の誤り（手掛かりのない地名は 2 通りの読みになるのが正しい）。もう 1 件は解析器の欠陥：`2月30日 0846` で、書かれた日付が読めなかったのに、時刻へ「今日」を補っていた。書いた日付を無視して推定で埋めるのは誤りなので、日付が読めなかったときは今日を補わないよう直した。
- **探りの入力で見つけた誤り（`docs/proto/fragment.md` に書いた）**：`2026` を 20:26 の時刻と読む。`5km` を深さと読む（距離かもしれない）。`震度4 5弱` で、規模として読む案だけが残る。この最後のものは、外した読みを `detail` に出すようにした。
- 実際の利用者の入力では試していない（模擬の入力だけ）。ブラウザでの読み込みも試していない（Node.js だけで動かした）。
- **個人語の検査は未実施。** 環境変数 `ESM_DENYLIST_FILE` が未設定で、フックがそのことを表示した。
- 日付：作業した日は日本時間で 2026-11-05。

## 誤り記録

- **解析器の欠陥（日付）**：上記の `2月30日` の件。書かれた日付が読めないとき、今日を補っていた。テストを書く過程で見つけ、同じ回のうちに直した。コミットした版の前に直したので、リポジトリには入っていない。
- **テストの期待の誤り**：手掛かりのない地名が 1 通りに決まるはずと書いていた。設計（候補を全部返す）と食い違っていたので、テストを直した。
- **`node --test` のディレクトリ指定**：最初に書いた実行コマンドが動かなかった。動く形に直して README に反映した。

## l4b へ戻す学び

- 「決めつけない」設計では、結果を値ではなく候補の配列にしておくと、曖昧な入力と曖昧でない入力を同じ形で扱える。
- 推定で補った値（今日、km、今年）は、値の横に推定の印を持たせ、`detail` にも書く。値だけだと、使う側が推定かどうか区別できない。
- 「読めない」の安全な出し方は、`null` や `unknown` にして、読めなかった部分を入力のまま残すこと。直して読むと、入力にない事実を足してしまう。
- 書いた日付が読めないときに今日で埋める、のような「補う処理」は、補ってよい条件（何も書かれていないとき）を狭く書く。
- 見逃しうる誤りは、「間違った値を読めたものとして返す」と「読むべきものを読まない」に分けると整理しやすい。前者の方が危ない。
